# ADR-001: 開発環境管理ツール効率化決定

## ステータス

提案中

## コンテキスト

### 現在の課題

Claude Code LXC環境の現在のセットアップ方法には以下の課題があります：

1. **複雑性**: 複数のパッケージマネージャー（apt、npm、pip3、rustup、curl）と手順の組み合わせ
2. **再現性の欠如**: 時期によりダウンロードされるバージョンが変動し、環境の一貫性が保証されない
3. **依存関係競合**: システムレベルでの競合リスク（特にNode.js環境）
4. **分散したバージョン管理**: 言語ごとに異なるツールでバージョン管理
5. **セキュリティリスク**: チェックサム検証なしのバイナリダウンロード
6. **メンテナンス負荷**: 手動セットアップスクリプトの複雑化

### 先進的コミュニティの動向

vim-jpのような先進的なコミュニティでは、以下のトレンドが観察されています：

- **miseとaquaの採用**: 2-3年前にデファクトスタンダード化
- **Nixパラダイムへの移行**: より完全な再現性を求める動き
- **LSPやTree-sitterなど外部依存の複雑化**: より強力な環境管理ツールへの需要

## 決定

以下の段階的アプローチで開発環境管理ツールを導入します：

### Phase 1: mise導入 (高優先度)

**対象範囲**: 
- Node.js、Python、Rust のバージョン管理統一
- 環境変数管理の統一化
- タスクランナー機能の活用

**利点**:
- 学習コストが低い
- 既存の`.tool-versions`ファイルとの後方互換性
- asdfからのスムーズな移行
- 環境変数とタスクの統合管理

### Phase 2: aqua導入 (中優先度)

**対象範囲**:
- GitHub CLI、kubectl、Docker関連ツール
- セキュリティ重要なCLIツール

**利点**:
- チェックサム検証によるセキュリティ強化
- 宣言的な依存関係管理
- 遅延インストールによる初期セットアップ高速化

### Phase 3: devbox統合検討 (検証フェーズ)

**対象範囲**:
- 完全な環境再現性の検証
- LXCとの併用可能性の評価

**利点**:
- Nixpkgsの80,000+パッケージへのアクセス
- バイト単位での環境再現性
- 複雑なNix学習なしでNixの恩恵を享受

## 実装計画

### 技術的実装

1. **mise.toml**の作成
   ```toml
   [tools]
   node = "lts"
   python = "3.11"
   rust = "stable"
   
   [env]
   NODE_ENV = "development"
   DOCKER_BUILDKIT = "1"
   
   [tasks.setup]
   run = "npm install && pip install -r requirements.txt"
   ```

2. **aqua.yaml**の作成
   ```yaml
   registries:
   - type: standard
     ref: v4.125.0
   
   packages:
   - name: cli/cli@v2.40.1
   - name: docker/cli@v24.0.7
   - name: kubernetes/kubectl@v1.28.4
   ```

3. **devbox.json**の作成
   ```json
   {
     "packages": [
       "nodejs@18",
       "python@3.11",
       "rustc@1.74",
       "github-cli",
       "kubectl",
       "docker"
     ],
     "shell": {
       "init_hook": [
         "echo 'Development environment initialized with devbox'"
       ]
     }
   }
   ```

### 移行戦略

1. **段階的導入**: 既存環境を破壊せず、新環境で並行テスト
2. **後方互換性**: 従来のセットアップ方法も継続サポート
3. **文書化**: 各ツールの使い分けガイドを作成
4. **検証**: 実際のプロジェクトでの動作確認

## 期待効果

### 短期効果 (mise + aqua導入)

- **セットアップ時間**: 30-50%短縮見込み
- **再現性**: バージョン固定により向上
- **セキュリティ**: aquaのチェックサム検証
- **メンテナンス性**: 宣言的設定による簡素化

### 中長期効果 (devbox統合)

- **完全再現性**: バイト単位での環境一致
- **依存関係解決**: システムレベルでの競合回避
- **スケーラビリティ**: 新しいツール追加の簡素化

## リスク

### 技術的リスク

1. **学習コスト**: 新ツールの習得時間
2. **成熟度**: devboxの安定性
3. **パフォーマンス**: 初回セットアップ時間

### 軽減策

1. **段階的導入**: 低リスクなツールから開始
2. **並行運用**: 既存方法との共存期間を設定
3. **フォールバック**: 従来方法への復帰手順を整備

## 代替案

### 検討したが採用しなかった案

1. **asdf継続**: パフォーマンス課題とRust実装の優位性からmiseを選択
2. **Nix直接導入**: 学習曲線の急峻さからdevboxを優先
3. **Docker Compose**: LXCとの重複とオーバーヘッドを考慮

## 関連決定

- 既存のLXCベース環境は継続
- VS Code Remote-SSH統合は維持
- セキュリティ強化（fail2ban、ufw）は継続

## 注記

この決定は、vim-jpコミュニティの先行事例と、「利便性の時代からNixパラダイムへの移行」という業界トレンドを踏まえています。段階的導入により、リスクを最小化しながら最新の開発環境管理手法を取り入れます。
